# О проекте
fees-service считает комиссии за переводы и операции по картам для розничных клиентов.
Вызывается синхронно из transfers-service и cards-service, ответ нужен за 50 мс (p95).
Ошибка в расчёте – это претензия клиента и отчёт регулятору, поэтому точность важнее скорости разработки.

# Архитектура
- api/        REST-контроллеры, точка входа FeeController
- core/       правила расчёта, класс FeeCalculator – сердце системы
- tariffs/    загрузка тарифов из справочника, кеш на 15 минут
- persistence/ JPA-репозитории, схема в db/migrations (Flyway)
- reporting/  выгрузки для регулятора, не трогать без согласования

# Договорённости
- Java 17, Spring Boot 3. Новые зависимости только из внутреннего реестра (см. allowed-deps.txt).
- Деньги – только BigDecimal, округление HALF_EVEN, никогда double.
- Логи в JSON через общий логгер, без номеров карт и счетов (только маскированные).
- Ошибки – исключения из core/errors, коды из errors.yaml.
- Публичный интерфейс: всё в api/ и схема базы. Меняется только через спецификацию.

# Как проверять
- ./gradlew test          – модульные, должны проходить всегда
- ./gradlew integration   – интеграционные, нужен Docker
- ./gradlew lint          – линтер по стандартам банка
До пул-реквеста: тесты и линтер зелёные, покрытие изменённых строк не ниже 70%.

# Чего не делать
- Не менять core/FeeCalculator и reporting/ без спецификации и ревью 2 сеньоров.
- Не добавлять миграции схемы без подтверждения человека.
- Не использовать реальные данные клиентов в тестах, только генератор fixtures/.
- Не запускать команды деплоя и не трогать файлы в deploy/.

# Порог спецификации
Через спецификацию (specs/): изменение api/, схемы базы, core/, больше одного модуля.
Без спецификации: исправление ошибки в одном модуле, тексты, тесты, рефакторинг внутри модуля.
